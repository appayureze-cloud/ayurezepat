# WhatsApp opt-in: consent endpoint (Phase 3)

## Why

The product plan uses WhatsApp (via a Business Solution Provider, BSP - e.g.
Gupshup/Twilio/360dialog) to send order status, dose reminders and
appointment confirmations. **The app never talks to the BSP directly and
never stores a BSP/WhatsApp API key client-side** (see the note in
`lib/const/env.dart`) - it only records the patient's opt-in/out choice with
our own backend via the endpoint below. The backend is the only thing that
calls the BSP, using the phone number and consent record it already has.

`WhatsappConsentRepository`
(`lib/features/whatsapp_consent/domain/whatsapp_consent_repository.dart`) is
written against this contract, mocked by default via
`Env.useMockWhatsappConsent`. The mock persists the choice locally
(SharedPreferences) so opting in/out actually sticks across app restarts in
demos, even with no backend.

## `POST /consents/whatsapp`

Request:

```json
{
  "opted_in": true,
  "phone": "+911234567890",
  "case_id": "case_123"
}
```

`case_id` is the patient's current active case if one exists (from
`Preferences.activeCaseId`, the same slot `CaseRepository`/Astra use) and is
omitted when there isn't one yet - this is an account-level preference, not
tied to a single case, but recording the case gives the backend an audit
trail of what triggered the opt-in.

Response:

```json
{
  "success": true,
  "data": {
    "opted_in": true,
    "consented_at": "2026-09-28T09:00:00Z"
  }
}
```

The backend should record `consented_at` as a server timestamp (not trust
a client-supplied one) - this is the compliance record of when/that the
patient consented, and needs to survive independently of the app's local
cache.

## `GET /consents/whatsapp`

Returns the patient's current choice, same response shape as above.
`opted_in` defaults to `false` (opt-in, not opt-out, matching how consent
should work) for a patient who has never called `POST /consents/whatsapp`.

## Client behavior

`WhatsappOptInScreen` (Profile > WhatsApp Updates) shows a single toggle
backed by this contract, plus the phone number messages will go to (from
`Preferences.phone`, set at login/signup) and a plain-language explanation
of what's sent. Toggling calls `POST /consents/whatsapp` immediately - there
is no separate "save" step. `WhatsappConsentRepositoryImpl` also caches the
last-known choice locally after every read/write so the toggle has
something to show immediately on next open, offline-first, the same way
`CaseRepository` caches `activeCaseId`.

## Astra safety note

Whatever the backend sends over WhatsApp, it must follow the same rule as
Astra chat: no diagnosis, no prescription, no dosage-adjustment advice sent
by WhatsApp message. Only status updates and reminders that were already
generated by a doctor/pharmacist-reviewed flow (e.g. "your order has
shipped", "time for your evening dose") belong here.

## Not yet specced

A therapy centre / provider-facing portal (for centre staff to view
bookings, mark attendance, etc.) was mentioned alongside this feature in the
original product brief but has no defined contract yet - it's a distinct,
larger piece of work (auth for centre staff, a different UI surface
entirely) and isn't part of this patient-app client. Flagging it here so
it isn't lost, not specifying it speculatively.
